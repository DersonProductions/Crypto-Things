# assumeutxo (quick reference)

This short note explains the general idea behind Bitcoin Core's "assumeutxo" feature and when it may be useful. It is intended as a conceptual reference for readers of this repository — always consult the Bitcoin Core documentation and release notes for exact command-line/configuration syntax and the correct hashes for any snapshot.

## Summary

`assumeutxo` is a mechanism that allows a validating node to start from a trusted UTXO set snapshot at a specific block height instead of reconstructing the full UTXO set by replaying and validating every historical block. The node still verifies block headers and consensus rules from that point forward, but it "assumes" the correctness of the UTXO set at the snapshot height to speed up initial sync.

## Why it exists

- Full validation from genesis can be slow on large chains because the node must process every transaction ever created to build the current UTXO set.
- A verified snapshot of the UTXO set lets new nodes skip the most expensive part of initial validation and get into a fully validating state much faster.

## High-level mechanics

- A snapshot is a representation (and hash) of the chainstate (the UTXO set) at a particular block height H.
- The node downloads headers up to the chain tip and checks proof-of-work and the header chain normally.
- Instead of reconstructing the UTXO set by reprocessing all blocks ≤ H, the node loads the provided snapshot and verifies that the snapshot corresponds to the block at height H (via a published snapshot hash or other metadata).
- After loading the snapshot, the node will validate subsequent blocks (H+1, H+2, ...) normally, enforcing consensus going forward.

Because headers and the block hash at height H are validated, the snapshot is not a completely blind trust — it is tied to the chain via the validated headers. However, trusting the snapshot requires trusting the provider of that snapshot (or verifying it by other means).

## Security trade-offs

- Pros:
  - Much faster initial sync for new nodes.
  - Reduces CPU and I/O required to reach a fully validating state.

- Cons / Risks:
  - If the snapshot provider is malicious or compromised, a node that blindly accepts an incorrect snapshot could be misled about the UTXO set at H. This could enable accepting invalid transactions until a conflicting state is detected.
  - The feature is only as secure as the source of the snapshot and the out-of-band verification of its authenticity (e.g., multiple trusted publishers, signed metadata).

## When to use

- Helpful for operators who need fast setup of many validating nodes (e.g., testing fleets, services, or developers).
- Useful when you can obtain a snapshot from a trusted source (same organization or a well-audited, reproducible process).
- Avoid using untrusted or unverified snapshots for production security-sensitive deployments unless you have an independent way to verify them.

## How to obtain a snapshot

- Snapshots can be generated by fully validating nodes by exporting the chainstate/UTXO set at a given height. They are sometimes distributed by maintainers or third parties.
- Best practice: generate your own snapshot from a node you control and fully validated, or obtain one from a provider you trust and verify its integrity (checksums, signatures, or cross-check with multiple sources).

## Operational notes

- After using a snapshot, monitor the node logs for any warnings about incompatibilities or reorgs near the snapshot height.
- Keep backups of any chainstate or config used to create the snapshot so you can reproduce or audit it later.
